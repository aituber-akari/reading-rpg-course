# 「読むRPG」を作りながら学ぶソフトウェア開発教材 仕様書

- 文書種別：教材制作仕様書
- 版：0.1（構想仕様）
- 作成日：2026年11月18日
- 教材の提供形式：HTML
- 教材で開発するプログラムの中心言語：TypeScript

## 1. 目的

「読むRPG」の最小実装（MVP）を題材に、プログラミング、アルゴリズム、Webアプリケーション開発、Git/GitHubによるソフトウェア管理、テスト、CI/CD、ソフトウェアファクトリー型の開発を、**演習・プロジェクト中心**に学べる教材を制作する。

学習者はゲームを段階的に作り、最後に次の三つのスケールが連動するWebアプリを完成させる。

1. **一瞬の行動**：状況・技能・装備・環境から行動を選び、問題を解決する。行動の組合せにより機転や奇策に見える展開が生じうる。
2. **キャラクターの人生**：目的・性格・記憶・成長によって行動が変わり、人生の軌跡が蓄積される。
3. **世界の歴史**：複数のキャラクターの出来事が同じ世界に残り、後の人物や出来事と結びつく。

各スケールでまず動作する最小限の作品を作り、最後に統合する。題材は研究・本格開発のための**MVP**であり、完成版「読むRPG」そのものを開発対象とはしない。

## 2. 教材設計の原則

### 2.1 演習・プロジェクト主導

- 各章は「何を作れるようになるか」から始める。
- 必要な文法・API・アルゴリズムは、作業時点で短い説明と実行可能なコード例を示す。
- 文法項目の網羅的な講義を前提にしない。最低限のTypeScript文法は序章で扱い、その後は制作課題に応じて追加する。
- 毎章、目に見える・実行できる成果（ログ、行動の違い、地図、保存、公開など）を得られるようにする。
- 各部を終えると、その部単独でも観察できるミニゲーム／シミュレータが残る。

### 2.2 段階的な複雑化

- 原則として、各章は前章までの完成物を拡張する。
- 行動、人物、世界のデータやロジックは再利用できるモジュールに分ける。
- 教材のための対象数は最小限にする（技能・装備・地形・人物・集落はいずれも少数から始める）。
- 複雑な機能を導入するときは、導入前後の振る舞いを同じシナリオで比較できるようにする。

### 2.3 観察できることを重視

- 行動や意思決定の理由と結果を、学習者がログで追えるようにする。
- 乱数を使う章では固定シードによる再現可能な例も用意する。
- 行動ログと、結果から読み手が想像する物語との関係を考えられる演習を設ける。

## 3. 想定する開発・実行環境

| 項目 | 仕様 |
|---|---|
| 言語 | TypeScriptを主言語とし、HTML/CSSを併用 |
| 開発対象 | ブラウザで動くWebアプリケーション |
| ビルド・開発用ツール | Node.js、npm、Vite、TypeScript |
| テスト | TypeScript対応の単体テスト環境（例：Vitest） |
| バージョン管理 | Git、GitHub |
| 自動化 | GitHub Actionsによる型チェック・テスト・ビルド・デプロイ |
| 公開 | GitHub Pages |
| データ保存 | JSONとブラウザの`localStorage` |
| 対応端末 | PC・スマートフォンのブラウザ（レスポンシブ画面） |
| 動作方式 | 静的サイトで動くクライアントサイド実行。教材MVPでは画面を開いている間、時間経過でゲームを進行させる |

学習に必要な技術を段階的に導入し、サーバ構築やDocker/WSLを必須としない。学習環境にローカルツールを導入できない場合の補助として、ブラウザベースの編集・実行環境を使用する手順も教材に用意する。具体的なサービス名・利用可能条件は教材制作時に確認する。

## 4. 全体構成

**序章＋全4部、計16章（序章を除く）**を基本構成とする。

| 区分 | テーマ | 完成物 |
|---|---|---|
| 序章 | 最初の冒険を動かす | 最小限のログRPG |
| 第1部（第1〜4章） | 一瞬の行動 | 状況に応じて行動・問題解決を行うシミュレータ |
| 第2部（第5〜8章） | キャラクターの人生 | 目的・記憶・成長を持つ人物の人生シミュレータ |

各章の番号・題名は教材制作時の識別子として固定し、教材HTML・完成版コード・テストに同じ番号を使う。

## 5. 章別仕様

### 序章：最初の冒険を動かす

**制作物**：冒険者が村を出発し、移動し、敵と遭遇する短いログを出力するプログラム。

**最小機能**：キャラクター名、HP、現在地、イベント列、ログ表示。最初はサンプルを実行し、数値・条件・文章を改造して結果を変える。

**学ぶ内容**：`const`/`let`、数値・文字列・真偽値、`if`、`for`、配列、オブジェクト、関数、基本の型注釈・`type`、モジュールの入口、実行方法、Gitのコミット。

**完成条件**：入力した設定によってログが変わり、型チェック・起動・再実行ができる。

### 第1部：一瞬の行動

#### 第1章：戦闘する冒険者

- **制作物**：攻撃・防御・逃走を選ぶ最小の戦闘シミュレータ。
- **最小機能**：HP、攻撃力、行動候補、行動選択、勝敗・逃走の判定。結果はイベントログとして出力する。
- **学ぶ内容**：条件分岐の整理、関数分割、型を使った状態管理、基本的なテスト。
- **完成条件**：同じ戦闘状況で、選ばれた行動によって結果が変わる。

#### 第2章：障害を乗り越える

- **制作物**：技能・装備・環境によって利用可能な行動が変わる障害突破シミュレータ。
- **最小機能**：技能（例：登攀・跳躍・魔法）、所持品（例：ロープ）、環境（例：崖・蔦・固定点）、行動の前提条件・効果・コスト。
- **学ぶ内容**：データ構造、集合／条件の判定、アフォーダンスの表現、ルールとデータの分離。
- **完成条件**：同じ崖でも、技能や持ち物、環境の違いで可能な突破手段が変わる。

#### 第3章：機転を利かせる

- **制作物**：複数の行動を組み合わせて目標を達成する計画シミュレータ。
- **最小機能**：状態、目標、行動の前提条件・効果、行動列の探索、行動コスト。例：「ロープを入手→固定→降りる」。
- **学ぶ内容**：状態空間、グラフ、幅優先探索（BFS）、ダイクストラ法、A*探索、ヒューリスティック。資源配分の別演習として動的計画法（DP）を扱う。
- **完成条件**：同じ問題に対し探索法を切り替え、得られる計画・コスト・探索ノード数を確認できる。複数の解決経路を持つ小規模な例題がある。

#### 第4章：行動を読ませる

- **制作物**：第1〜3章の内部イベントから、簡潔な自然言語ログを生成するプログラム。
- **最小機能**：イベント種別、行為者、対象、結果、時刻または順番を構造化して記録し、表示形式を切り替える。
- **学ぶ内容**：データと表示の分離、イベントモデル、テンプレート文字列、ログ整形。
- **完成条件**：同じイベント列を、詳細ログと簡潔なログの少なくとも2通りで表示できる。

**第1部の成果**：技能・装備・環境を踏まえ、目標に向けて行動するキャラクターの短い場面を、ログとして読むことができる。

### 第2部：キャラクターの人生

#### 第5章：意志を持つ冒険者

- **制作物**：目的や性格によって行動選択が変わるキャラクター。
- **最小機能**：目標（探索・休息など）、性格を表す少数の重み、候補行動の評価・選択。
- **学ぶ内容**：有限状態機械、スコアに基づく意思決定、関数とモジュールの設計。
- **完成条件**：能力が同じでも、異なる目標・性格の人物が別の行動を選びうる。

#### 第6章：記憶する冒険者

- **制作物**：過去の経験を次の判断に反映するキャラクター。
- **最小機能**：訪問地、遭遇、成功・失敗などの記憶を蓄積し、判断時に参照する。
- **学ぶ内容**：配列・連想データ・検索、履歴の管理、データモデルの変更。
- **完成条件**：一度経験した出来事が、その後の行動選択に影響する例を再現できる。

#### 第7章：成長する冒険者

- **制作物**：経験から能力や行動傾向が変化するキャラクター。
- **最小機能**：技能の成長、資源の回復、経験の反映。成長規則は少数に限定する。
- **学ぶ内容**：状態遷移、更新規則、シミュレーションの再現性、回帰テスト。
- **完成条件**：同じ課題でも、経験前後で選択・成功条件・結果のいずれかが変化する。

#### 第8章：一人の人生

- **制作物**：活動・休息・移動・遭遇が時間とともに連続する人生シミュレータ。
- **最小機能**：時刻／日付、行動サイクル、イベント履歴、人生を俯瞰する要約表示。
- **学ぶ内容**：シミュレーション時間、イベント駆動処理、長期実行のテスト、ログの集約。
- **完成条件**：一人の人物について、短い行動記録と長期的な人生の履歴を読み分けられる。

**第2部の成果**：行動の蓄積が記憶・成長・目的に結びつき、一人の人物が継続的に活動する様子を観察できる。

### 第3部：世界の歴史

#### 第9章：世界を生成する

- **制作物**：村・道・ダンジョンがつながった小さな世界。
- **最小機能**：地点と経路を生成・保持し、文字や記号で簡易地図を表示する。
- **学ぶ内容**：グラフ表現、手続き型生成、乱数シード、基本の経路探索。
- **完成条件**：異なるシードで複数の世界を生成し、地点間のつながりを確認できる。

#### 第10章：世界に人を住まわせる

- **制作物**：複数のキャラクターが同じ世界で活動するシミュレータ。
- **最小機能**：複数人物の配置・移動・遭遇、共通の時刻・場所の管理。
- **学ぶ内容**：複数エージェントの更新、データの参照関係、処理順序の設計。
- **完成条件**：別々に活動していたキャラクターが同じ場所で出会い、その出来事が記録される。

#### 第11章：世界を変化させる

- **制作物**：人物の行動が世界の状態に変化を残すシミュレータ。
- **最小機能**：地点の発見、道の開通、集落の状態変更など、少数の永続的な変化。
- **学ぶ内容**：共有状態の更新、イベント処理、更新前後の整合性、統合テスト。
- **完成条件**：ある人物が起こした変化を、後から行動する別の人物が認識できる。

#### 第12章：歴史を記録する

- **制作物**：人物・場所・出来事の関係をたどれる歴史ログ。
- **最小機能**：人物ID、場所ID、イベントID、時系列の記録、過去の人物・場所の再登場、簡単な歴史の要約。
- **学ぶ内容**：ID・参照関係、イベント履歴、時系列検索、履歴に基づく表示。
- **完成条件**：過去の出来事と現在の人物・場所との関係が、ログからたどれる。

**第3部の成果**：キャラクターの活動によって世界の状態と履歴が変化し、複数の人物の出来事が一つの歴史に積み重なる。

### 第4部：読むRPGへ統合

#### 第13章：ゲーム画面を作る

- **制作物**：ログ・人物情報・簡易地図を閲覧するWeb UI。
- **最小機能**：ログ一覧、人物情報、地点のつながりを示す地図、実行・一時停止の操作。
- **学ぶ内容**：HTML、CSS、DOM操作、イベントハンドラ、レスポンシブ設計。
- **完成条件**：PC・スマートフォン双方で主要情報を閲覧・操作できる。

#### 第14章：世界を保存する

- **制作物**：ブラウザを閉じても状態を復元できるアプリ。
- **最小機能**：キャラクター・世界・履歴のJSON化、`localStorage`への保存・読込、初期化。
- **学ぶ内容**：シリアライズ、保存データの構造、読み込み時の検証、データ形式のバージョン管理。
- **完成条件**：保存・再読込後に人物・地点・履歴が一貫して復元される。

#### 第15章：時間を進める

- **制作物**：ブラウザを開いている間、人物が自律的に動き続けるゲーム。
- **最小機能**：一定間隔でゲーム内時間を進める、進行速度の変更、一時停止、直近イベントの表示。
- **学ぶ内容**：時間管理、タイマー、表示とシミュレーションの分離、実行状態の制御。
- **完成条件**：動作中はログが継続的に追加され、停止・再開しても状態が破綻しない。

#### 第16章：公開する

- **制作物**：GitHub上で管理・自動検証され、GitHub Pagesで公開される読むRPGのMVP。
- **最小機能**：型チェック、テスト、ビルド、デプロイをGitHub Actionsに統合し、公開URLから起動する。
- **学ぶ内容**：CI/CD、ビルド成果物、デプロイ、Issue→変更→レビュー→統合→公開の開発サイクル。
- **完成条件**：公開URLからPC・スマートフォンで実行でき、リポジトリへの変更で自動検証が走る。

**第4部の成果**：一瞬の行動・人生・歴史をログとして観察できる最小の読むRPG Webアプリ。

## 6. 計画アルゴリズムの扱い（第2・3章を中心に）

### 6.1 アフォーダンスと行動モデル

対象物や環境が提供する行動の可能性をデータとして表す。行動が実行可能かどうかは、キャラクターの技能・装備・現在状態・環境条件の組合せで判定する。

MVPで扱う最小要素：

| 要素 | 例 |
|---|---|
| キャラクターの技能 | 登攀レベル、跳躍レベル、魔法の使用可否 |
| 所持品・装備 | ロープ、杖 |
| 環境 | 崖、蔦、固定点、倒木 |
| 行動 | 登る、ロープを固定する、渡る、魔法を使う |
| 前提条件 | 技能レベルが足りる、所持している、対象が存在する |
| 効果 | 位置が変わる、ロープが固定される、体力が減る |
| コスト | 行動回数、体力消費など |

行動は少なくとも「ID／前提条件／効果／コスト」を持つ。計画探索ではこの行動定義を共有し、探索法だけを差し替えられる構造とする。

### 6.2 探索アルゴリズム

| 手法 | 教材で確かめる点 | 例題 |
|---|---|---|
| BFS | 行動回数が最小となる計画 | 崖の向こうに行く最短手順 |
| ダイクストラ法 | 非負の行動コストの総和が最小となる計画 | 体力消費を抑えた突破方法 |
| A* | ヒューリスティックによる探索順序と探索量の違い | 地点や障害を含む目標到達 |
| 動的計画法 | 状態・段階ごとの部分問題の再利用 | 複数障害に対する限られた体力・魔力の配分 |

BFS・ダイクストラ法・A*は共通の小さな問題を使って比較し、動的計画法は資源配分問題の別演習で扱う。各実装は固定したテストケースを備える。

### 6.3 「機転・奇策」の最低限の実装範囲

- 通常の直接行動に加え、**複数の行動を組み合わせた代替経路**が存在する問題を用意する。
- 例：崖を直接登る／蔦を利用する／ロープを入手して固定する、といった異なる解決法を得る。
- アルゴリズムはそれらの候補を探索・評価し、ログに「何をしたか」と「どう状況が変わったか」を残す。
- 発展課題として、行動や環境データを追加すると新たな解決法が現れることを確かめる。

## 7. HTML教材の仕様

### 7.1 提供単位

- 教材全体のトップページ（学習案内・各部への目次）をHTMLで作る。
- **序章および第1〜16章それぞれに独立したHTMLページ**を用意する。
- 各部に概要ページを設け、成果物と学習する内容の関係を示す。
- 必要な文法や用語の短い説明を共通資料として参照できるようにする。
- HTML教材自体は静的に閲覧・公開できる構成とする。

### 7.2 各章のページに必ず含める要素

1. **今回作るもの**：目標、期待される動作、完成イメージまたは出力例。
2. **出発点**：前章の完成版との差分、使用する初期コード。
3. **演習**：実装する機能、編集対象ファイル、実行手順。短い課題を順に解く。
4. **必要な知識**：その課題で使う文法・API・アルゴリズムの最小限の説明とコード例。
5. **動作確認**：操作手順、期待ログ、確認する観点。
6. **テスト**：自動テストの実行方法と主な確認項目。
7. **完成版コード**：章の最終状態のソース一式へのリンク。主要ファイルの解説。
8. **振り返り**：今回追加したゲーム上の機能と習得した技術の対応。

### 7.3 演習提示の形式

- 基本形は「動作例を見る→サンプルを改造する→機能を自力で追加する→完成版と照合する」。
- 文法解説は演習の直前または横に配置し、必要な構文をその場で参照できるようにする。
- コード例はコピー・実行可能な形で掲載する。
- 各章で必須課題と、興味に応じて試せる発展課題を区別する。
- 完成版コードへのアクセスは制限せず、学習者が実装例を読み解けるようにする。

### 7.4 画面上の基本要素

- 全体目次、部・章の現在位置、前後の章への移動。
- 章の目的、演習本文、コード表示、実行結果例、完成版リンク。
- PC・スマートフォンで文章とコードを閲覧できるレイアウト。
- 見出し・コード・ログ表示の視覚的な区別。

## 8. 各章の完成版コード作成仕様

**この仕様書に基づいて教材を制作するときは、序章および第1〜16章の各章について、その章の課題をすべて実装した「完成版コード」を必ず作成する。** 最終章だけの完成版やコード断片の寄せ集めで代替しない。

### 8.1 成果物のセット

各章について、以下の3点を対応づけて提供する。

| 成果物 | 内容 |
|---|---|
| 教材ページ | `chapters/chXX.html`（序章は`ch00.html`） |
| 演習用コード | 学習者が編集して課題を進める初期状態のプロジェクト |
| 完成版コード | 当該章で求める機能がすべて実装され、独立して起動・確認できるプロジェクト一式 |

完成版には、必要なソースコード、設定ファイル、依存関係定義、テスト、READMEを含める。後続章の完成版が前章に変更を加える場合でも、**前章時点の完成版を残す**。

### 8.2 完成版コードの必須要件

1. **章ごとに実行可能**：対応する章の完成版を取得し、READMEの操作で起動できる。
2. **全ファイル提供**：`src`の一部だけでなく、ビルド・実行に必要な設定まで含める。
3. **教材との一致**：ページの出力例・仕様・課題と、完成版の振る舞いが一致する。
4. **前章からの発展が分かる**：今回追加・変更したファイルや関数をREADME等で示す。
5. **検証可能**：自動テストがあり、実行コマンドと期待される結果を明示する。
6. **再現可能**：乱数を使う場合は固定シードで同じ結果を得られる例を設ける。
7. **最小限の実装**：教材で扱わない本格的な機能を完成版に先取りして混入させない。
8. **統合可能**：部をまたいで使うデータ構造・モジュールの関係が説明できる。

## 9. GitHub・テスト・ソフトウェアファクトリーの学習仕様

開発手法は各部に横断的に組み込む。別建ての座学に偏らず、**その章のゲーム機能を作るために実際に使う**。

| 段階 | 学習・演習する内容 |
|---|---|
| 序章 | リポジトリ、コミット、差分、README |
| 第1部 | Issue、ブランチ、単体テスト、アルゴリズムのテストケース |
| 第2部 | モジュール分割、Pull Request、レビュー、リファクタリング、回帰テスト |
| 第3部 | 統合テスト、GitHub Actionsによる自動検証、複数モジュール間の変更管理 |
| 第4部 | ビルド・自動デプロイ、仕様と実装の対応、AI支援を含むソフトウェアファクトリー型の開発サイクル |

### 9.1 ソフトウェアファクトリー型演習の最低要件

第4部には、例えば小さな機能追加を対象に、次を一続きで体験する演習を用意する。

1. 欲しいゲームの振る舞いをIssue／短い仕様に記述する。
2. 仕様から受入条件とテストケースを整理する。
3. 実装し、必要に応じてAIによるコード生成・修正支援を利用する。
4. 型チェック・テスト・ビルドを自動実行する。
5. 差分とテスト結果を確認し、レビューして統合する。
6. 公開版に反映された動作を確認する。

人が書く工程とAIを利用する工程を同じ課題で比較・体験できる設計とする。AIツールは特定の有料サービスを必須とはしない。演習はAIなしでも完了できる。

## 10. 最終MVPの機能要件

| ID | 要件 | 最低限の受入条件 |
|---|---|---|
| FR-01 | キャラクターの作成 | 少数の技能・所持品・目的・性格を設定できる |
| FR-02 | 行動生成 | 状態・技能・装備・環境から実行可能行動が決まる |
| FR-03 | 行動計画 | 少なくとも1種類の探索法で、複数行動の計画を作れる |
| FR-04 | 行動結果の反映 | 行動により位置・資源・環境状態などが変化する |
| FR-05 | 人生の進行 | 人物が時間とともに行動し、経験や記憶が残る |
| FR-06 | 世界の共有 | 複数人物が同じ地点・世界状態を参照する |
| FR-07 | 歴史の蓄積 | 人物・場所・出来事を識別し、過去との関連を確認できる |
| FR-08 | ログ閲覧 | 一瞬の行動、人生の履歴、世界の出来事をそれぞれ閲覧できる |
| FR-09 | 簡易地図 | 地点と道のつながり、人物の現在地が分かる |
| FR-10 | 時間制御 | 実行・停止・再開・進行速度変更ができる |
| FR-11 | セーブ・ロード | `localStorage`で世界・人物・履歴を保存・復元できる |
| FR-12 | Web公開 | GitHub Pages上でPC・スマートフォンから動作する |
| FR-13 | 開発自動化 | GitHub Actionsで型チェック・テスト・ビルド・公開を行う |

最終画面は、**冒険ログ／キャラクター情報／簡易地図／履歴の閲覧／時間操作**を基本構成とする。グラフィックや音声を多用せず、数字と短い自然言語ログから出来事を想像する体験を中心に置く。
