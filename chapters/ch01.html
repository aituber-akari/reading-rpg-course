第1部 一瞬の行動 ／ 第1章

戦闘する冒険者

草原でアリアの前に灰色オオカミが現れる。攻撃するか、身を守るか、逃げるか。毎ラウンドの行動を選ぶ「方策」を差し替えると、同じ戦いの結末が変わる。乱数にシードを与えて、偶然の要素も再現できるようにする。

  • 目安 3〜4時間
  • TypeScript：関数分割、型による状態管理、関数を値として渡す
  • テスト：単体テスト、固定値の乱数、スナップショット
  • Git：ブランチ

今回作るもの

攻撃・防御・逃走を選ぶ1対1の戦闘シミュレータ。主人公の方策とシードを引数で切り替えられる。完成版を引数なしで動かすと、次のように表示される。

期待される動作：

  • 毎ラウンド、両者が行動を宣言し、素早さ（agi）の高い順に解決する。防御はそのラウンドの最初から効く。
  • HPが0になった側は「倒れた」状態になり、戦闘が終わる。逃げ切った場合も終わる。20ラウンドで決着しなければ引き分け。
  • 同じシード・同じ方策なら、何度実行しても同じログになる。

この章の完成条件は、同じ戦闘状況で、選ばれた行動によって結果が変わること。

出発点

序章の完成版を広げる。ファイルが増えるので、この章の演習用コード（starter）を新しい作業場所に写して始める。乱数生成器（src/lib/rng.ts）は完成品が入っている。

演習

戦闘を動かして比べる → 規則を読む → 方策を自分で書く、の順に進める。

必須演習 1-1 方策とシードを変えて比べる

次の3点をログで確かめる。(1) 同じシード・同じ方策なら同じログになる。(2) シードを変えるとダメージの値が変わる。(3) シード42では cautious と aggressive のログが一致する。3つ目は、アリアのHPが一度も30%（6）以下にならず、cautious が一度も防御を選ばないためである。

知識：シード付きの乱数

コンピュータの乱数の多くは、決まった計算で「乱数らしい」数の列を作る。最初の値（シード）が同じなら、同じ列が出てくる。この教材では Math.random を使わず、必ず次の生成器を引数で渡す。こうすると、偶然を含む戦闘でも結果を再現でき、テストでは決めた値を返す偽の生成器に差し替えられる。

int(-1, 1) は −1、0、1 のどれかを返す。ダメージの揺らぎに使う。

必須演習 1-2 規則を読み、ログと照らし合わせる

読むファイル：src/rules/combat.ts

ダメージと逃走の規則は次の2つの関数にある。

  1. アリア（攻撃力6）がオオカミ（防御力1）に与えるダメージは、揺らぎを含めて何〜何になるか。オオカミからアリア（防御力2）へはどうか。今回作るもののログの値が、その範囲に入っていることを確かめる。
  2. アリア（素早さ5）がオオカミ（素早さ6）から逃げ切る確率を求める。
答え

アリア→オオカミは 6 − 1 + (−1〜1) で 4〜6、オオカミ→アリアは 5 − 2 + (−1〜1) で 2〜4。逃げ切る確率は 0.5 + 0.1 × (5 − 6) = 0.4。

知識：関数を値として渡す（方策の型）

TypeScriptでは、関数も値として変数に入れたり、引数で渡したりできる。方策は「世界状態と自分・相手のIDを受け取り、行動を1つ返す関数」として型を決めてある。

'attack' | 'defend' | 'flee' は、この3つの文字列のどれかしか入らない型である。(world, selfId) => … は関数を短く書く形（アロー関数）で、使わない引数は書かなくてよい。手本の cautious は次のとおり。

world.entities[selfId] は、見つからなければ undefined になりうる（この教材の設定で、TypeScriptにそう扱わせている）。そのため先に undefined の場合を処理する。

知識：Gitのブランチ

ブランチは、履歴の流れを分けて作業する仕組み。演習用のブランチで試し、うまくいったら元のブランチ（main）に取り込む（マージする）。失敗しても main は汚れない。

必須演習 1-3 「HPが半分以下なら逃げる」方策を書く

編集するファイル：src/sim/policies.ts の retreatAtHalf（TODO）

HPが最大HPの半分以下なら 'flee'、それ以外は 'attack' を返す方策を書く。今は呼ばれると「未実装」のエラーを投げる。

実装したら、演習用のテストで確かめ、ログでも確かめる。

テストが通ったらコミットし、main に取り込む。

完成版の実装を見る

注意

シード42では、アリアのHPが半分（10）以下にならないまま勝つので、retreatAtHalf のログは cautious と同じになる。違いを見るには、動作確認のようにシード3を使う。「方策が違っても同じ結果になる状況がある」ことも、観察の結果の一つである。

発展演習 1-A あと一撃なら逃げない

シード3の retreatAtHalf では、オオカミの残りHPが1なのにアリアは逃げる。相手のHPも見て、「自分の最小ダメージで倒せるなら攻撃する」方策を書き、ログを比べる。damageOf の式から最小ダメージを求める関数を作るとよい。完成版には含まれない。

発展演習 1-B 敵の方策も選べるようにする

src/main.ts に引数 --enemy-policy を加え、敵も cautious などにできるようにする。両者が防御を続けると引き分けになることを確かめる。自分のGitHubのリポジトリで、この変更を先にIssueとして書いてから、ブランチを作って進めてみるとよい。完成版には含まれない。

必要な知識

演習のそばに置いた説明（シード付きの乱数、関数を値として渡す、ブランチ）に加えて、規則の組み立て方とテストの書き方をまとめる。

関数分割：規則・進行・方策・叙述

序章では1つのファイルが持っていた役割を、この章で分ける。分けておくと、それぞれを別々にテストでき、差し替えられる。

役割場所知っていること
規則rules/combat.ts1ラウンドで何が起きるか。乱数は引数で受け取る
進行sim/battle.ts決着までラウンドを繰り返すこと
方策sim/policies.ts状況を見て行動を選ぶこと
叙述narration/format.ts出来事を文にすること。戦闘の規則は知らない

型による状態管理と、元を書き換えない更新

人物の状態は 'alive' | 'down' のどちらかしか取れない。書き間違い（'dead' など）は型チェックで見つかる。resolveRound は最初に structuredClone(world) で世界状態を丸ごと複製し、複製だけを書き換えて返す。元の世界状態が変わらないので、「同じ初期状態から行動だけを変えた3通り」をテストで比べられる。

単体テストと、決めた値を返す乱数

Vitest のテストは describe（まとまり）、it（1つの確認）、expect(実際).toBe(期待) で書く。乱数を使う規則は、決めた値を順に返す偽の生成器 fixedRng でテストする。next() が 0.5 を返すと、int(-1, 1) は 0 になり、揺らぎのないダメージを確かめられる。

シード42の戦闘全体はスナップショット（前回の結果を保存したファイル）と比べる。規則を変えて結果が変わると、テストが知らせる。意図した変更なら npx vitest run -u で更新する。

文献コラム

人物は「多状態の物」である

Pinchbeck（2009）は、ゲームの物を状態とパラメータで記述した。パラメータが閾値に達すると状態が切り替わる。壊れる木箱がその例である。自律して動くagentも、この見方では「AIの付いた多状態の物」になる。この章の人物は、その最小の形をしている。

理論の概念この章の実装
状態
state: 'alive' | 'down'。倒れた人物は行動しない
パラメータ
hp、maxHp、atk、def、agi
閾値による状態遷移
HPが0以下になると down になる（resolveRound の if 文）
入力に応じた選択（SELECT）
方策 Policy。状況を見て行動を1つ選ぶ

この書き方の限界：この章では「HPが0以下なら倒れる」という規則を、resolveRound の中の if 文として手続き的に書いた。規則がコードの中に埋まっているので、(1) 蔦の強度が0になると切れる、のような別の物に同じ形の規則を使い回せない。(2) 規則をデータとして保存・表示・分析できない。(3) 規則を足すたびに関数を書き換えることになる。

第2章への橋渡し：第2章では、状態の切り替えを「どの状態から、どの状態へ、どの条件で」というデータ（遷移規則）として書く。たとえば蔦は、強度が0以下になると intact から torn に変わる、とデータで宣言する。第5章では、この章の戦闘そのものも宣言的な行為定義に移す。パラメータ名と出来事の形は、そのときも変えない。

参考：Pinchbeck, D. (2009). An affordance based model for gameplay. Proceedings of DiGRA 2009.　詳しくは設計思想：アフォーダンス。

動作確認

  1. npm start を2回実行し、まったく同じログになることを確かめる。
  2. 演習 1-3 の後、npm start -- --seed 3 --policy retreatAtHalf を実行する。
  3. 同じシードで --policy aggressive も実行し、結末を比べる。
  4. npm start -- --mode adventure で、序章の冒険が引き続き動くことを確かめる。

同じシード3でも aggressive なら、アリアは最後まで攻撃し、HP6を残してオオカミを倒す。オオカミの残りHPが1だったことを知っている読み手には、逃げたアリアの判断が惜しく見えるかもしれない。数字と短い文から、読み手はそこまで想像できる。

確認する観点：

  • 同じシード・同じ方策なら同じログ、方策を変えると結末が変わりうる。
  • HPが半分以下になった直後のラウンドで、アリアが逃走を選んでいる。
  • 序章の機能が壊れていない。
