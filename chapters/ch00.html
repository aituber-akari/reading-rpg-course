序章

最初の冒険を動かす

冒険者が村を出発し、森を抜け、敵に出会う。その短い記録を出力するプログラムを動かし、名前やHPや道のりを書き換えて、ログの変わり方を確かめる。最後に「休む」という手順を自分で足す。

  • 目安 2〜3時間
  • TypeScript：const/let、型、if、for、配列、オブジェクト、関数
  • Git：最初のコミットと差分

今回作るもの

主人公の設定と道のりを受け取り、出来事を順に処理して、1行ずつのログを出すプログラム（コマンドラインで動く）。完成版をそのまま動かすと、次のように表示される。

期待される動作：

  • 最初に「出発」の出来事が出て、そのときのHPが表示される。
  • 敵に遭遇するとHPが敵の強さ（power）だけ減り、減る前と後が表示される。HPは0未満にならない。
  • HPが0になると「倒れた」の出来事が出て、残りの道のりは処理しない。
  • 乱数を使わないので、同じ設定なら何度実行しても同じログになる。

この章の完成条件は、入力した設定によってログが変わり、型チェック・起動・再実行ができること。

出発点

最初の章なので、前章の完成版はない。教材のリポジトリにある演習用コード（starter）から始める。必要なものは Node.js 24 以上、Git、テキストエディタの3つ。

写したフォルダには次のファイルがある。データは上から下へ流れる。

ファイル役割
src/domain/types.ts型の定義：人物（Agent）、道のりの1手（Step）、出来事（WorldEvent）、変化（Change）
src/content/scenario.ts冒険の設定：主人公、道のり、場所の名前。演習で書き換える
src/adventure.ts道のりを順に処理して、出来事の列を作る（runAdventure）
src/narration/format.ts出来事を日本語の1行にする（formatEvent、formatLog）
src/main.ts入口。上の3つを組み合わせて、ログを表示する
設定（scenario.ts）→ runAdventure → 出来事の列（WorldEvent[]）→ formatLog → 文字列の列 → 画面

ゲームの「出来事」と、それを読む「文」を分けて持つのがこの教材の基本の形である。出来事はデータなので、テストで確かめたり、後の章で別の書き方のログにしたりできる。

演習

動作例を見る → サンプルを改造する → 機能を自力で追加する → 完成版と照合する、の順に進める。文法の説明は、それを使う演習のすぐ前に置いた。

必須演習 0-1 そのまま動かす

作業フォルダで次を実行し、今回作るものと同じ5行が出ることを確かめる。

npm start は package.json に書いた tsx src/main.ts を実行する。tsx はTypeScriptのファイルを、変換の手間なしにそのまま実行する道具である。

知識：値と変数（const／let）

値には数値（12）、文字列（'リナ'）、真偽値（true／false）などがある。名前を付けて値を持つには const を使う。あとで別の値を入れ直す変数だけ let にする。

知識：オブジェクト・配列・型注釈

オブジェクトは { 名前: 値 } の組、配列は [値, 値, …] の並び。interface で「どんな名前の値を持つか」を型として書いておくと、書き間違いを型チェックが見つける。人物の型は次のとおり。

const hero: Agent = { … } のように、変数名の後ろに : 型 を書くのが型注釈である。params のようにオブジェクトの中にオブジェクトを入れることもできる。

必須演習 0-2 設定を変えて、ログを変える

編集するファイル：src/content/scenario.ts

主人公と道のりは次のように書いてある。名前、HP、敵の名前や強さ（power）を書き換えて、npm start を実行し直す。

  1. 名前を自分の好きな名前にする。ログの全行が変わることを確かめる。
  2. HPを 6 にする。2回目の遭遇で倒れ、ログが6行になる（動作確認に期待ログがある）。
  3. 道のりの最後に、{ kind: 'encounter', enemy: { id: 'goblin', name: 'ゴブリン', power: 5 } } のような3体目の敵を加える。移動先には placeNames にある場所のID（village・forest・cave-entrance）を使うと、名前で表示される。

型と違う値を書くと、npm run typecheck がエラーを出す。たとえば hp: '12'（文字列）と書いて確かめてみるとよい。

知識：Gitのリポジトリ・コミット・差分

Gitはファイルの変更の履歴を記録する道具。履歴を記録する場所をリポジトリ、ある時点の状態を記録したものをコミット、2つの状態の違いを差分という。コミットする前に、記録したい変更を git add で選ぶ。

必須演習 0-3 最初のコミット

作業フォルダをGitのリポジトリにして、元の状態を記録する。node_modules/ は npm ci で作り直せるので、記録しないよう .gitignore に書く。

次に、主人公の名前とHPを書き換えて、差分を見てからもう一度コミットする。

git diff では、消した行が -、足した行が + で表示される。git log --oneline にコミットが2つ並べば完了。

注意

git commit の前に、名前とメールアドレスの設定を求められることがある。表示された git config --global user.name と user.email のコマンドで設定する。GitHubで公開する予定があるなら、メールアドレスはGitHubの非公開用アドレスにしておくとよい。

知識：if・for と「種類で分かれる型」

道のりの1手（Step）は、kind の値によって持つ情報が変わる。| でつないだこの型を判別共用体という。

for (const step of steps) で配列を先頭から1つずつ取り出し、if (step.kind === 'move') で種類を調べる。if の中では、TypeScriptが step を move の形だと分かっているので、step.to が使える。どれにも当たらなかった最後の else では、残りの種類（rest）だけが来る。

知識：関数と、元を書き換えない更新

関数は引数を受け取り、値を返す。引数と戻り値にも型を書く。

runAdventure は、受け取った主人公を書き換えずに新しいオブジェクトを作る。{ ...current, params: { ...current.params, hp: after } } は「current の中身を写し、params の hp だけ差し替えた新しいオブジェクト」という意味である（... はスプレッド構文）。元のデータが変わらないので、テストで前と後を比べやすい。

必須演習 0-4 「休む」手順を足す

編集するファイル：src/adventure.ts、src/narration/format.ts の TODO（と、試すときは src/content/scenario.ts）

型 Step にはすでに { kind: 'rest'; amount: number } がある。けれども今は、休んでも何も起きず、ログには「（未実装：休む）」と出る。次の2つを実装する。

  1. runAdventure の最後の else：HPを step.amount だけ増やし、action: 'rest' の出来事を出す。HPの変化（Change）も記録する。すぐ上の遭遇（encounter）の処理がよい手本になる。
  2. formatEvent の rest：「休んだ」を含む文を作る。hpText(e) で「HP 9→12」の文字列が得られる。

テストが通ったら、scenario.ts の道のりの、スライムとの遭遇の後に { kind: 'rest', amount: 3 } を加えて、ログで確かめる（動作確認）。最後にコミットする。

完成版の実装を見る

発展演習 0-A 休んでも最大HPを超えない

今の「休む」は、HPをいくらでも増やせる。人物に最大HP（例：maxHp）を持たせ、休んでもそれを超えないようにする。Agent の型、hero の設定、runAdventure の3か所を変えることになる。第1章では、人物が実際に maxHp を持つ。完成版には含まれない。

発展演習 0-B 新しい種類の手順

たとえば「宝箱を開ける」のような新しい手順を Step に加える。型に1行足すと、runAdventure の if の分岐がどこで足りなくなるかを、型チェックがどう知らせるか観察する。完成版には含まれない。

必要な知識

この章の文法は、演習のそばに置いた。ここではその一覧と、ファイルをまたぐ仕組みをまとめる。

項目使う場所説明

オブジェクト・配列・interface・型注釈scenario.ts、types.tsオブジェクト・配列・型注釈

リポジトリ・コミット・差分端末Gitの基本

モジュール：import と export

1つのファイルが1つのモジュールである。他のファイルから使わせたいものに export を付け、使う側は import で読み込む。型だけを読み込むときは import type と書く。プログラムの入口は src/main.ts で、ここだけが画面への表示（console.log）を行う。

型チェックと実行は別のもの

npm start（tsx）は型を確かめずに実行する。型の誤りを見つけるのは npm run typecheck（tsc --noEmit）の役目である。npm run check は型チェックとテストを続けて行う。

文献コラム

ログという「物」を、読み手が読む

Pinchbeck（2009）は、ゲームの中の物を、遊びを進めるもの（ゲームプレイ系）と、物語世界を支えたり筋の理解を進めたりするもの（物語系）とに分けて整理した。読むRPGの読み手は人物を操作しない。読み手の手元にあるのはログだけであり、ログの1行1行が、読み手に解釈を促す物語系の「物」として働く。

理論の概念この章の実装
パラメータを持つ物
人物 Agent の params: { hp }。人物も「数値を持つ物」として書き始める
出来事の記録
WorldEvent と Change（HPの前と後）。ログはここから作る
物語系の物（story object）
formatLog が作るログの1行。「HP 12→9」の数字と短い文から、読み手がその間の出来事を想像する

出来事（データ）と文（叙述）を分けておくと、同じ出来事の列を別の書き方で読ませられる。第4章では、同じ出来事から詳細ログと簡潔ログを作り、読み手が受け取る物語の違いを観察する。

参考：Pinchbeck, D. (2009). An affordance based model for gameplay. Proceedings of DiGRA 2009.　詳しくは設計思想：アフォーダンス。

動作確認

  1. npm start を2回実行し、まったく同じログが出ることを確かめる。
  2. scenario.ts の HP を 6 にして実行する。
  3. HP を 12 に戻し、スライムとの遭遇の後に { kind: 'rest', amount: 3 } を加えて実行する（演習 0-4 の後）。

確認する観点：

  • 設定を変えると、ログが変わる。変えなければ、何度でも同じログになる。
  • 倒れた後の道のりは処理されない。
  • 「休む」の文の文面は自分の書いたものでよい。「休んだ」を含み、HPの変化が表示されていればよい。

テスト

テストは Vitest で書いてあり、tests/adventure.test.ts に次の項目がある。

前提（Given）期待（Then）
主人公の名前が「リナ」ログの1行目に「リナ」と「出発」が含まれる
既定の道のり出来事の種類が action, action, encounter, action, encounter の順に並び、ログが設計どおりの5行になる
HP 62回目の遭遇で HP 3→0 となり、「倒れた」の後に出来事はない
遭遇のダメージがHPを上回るHPは0未満にならない
名前とHPが異なる2つの設定ログが異なる（完成条件）
任意の設定で実行引数に渡した主人公のHPは変わらない
演習：HP 5 で rest（amount 3）HP 5→8 の変化が記録され、ログに「休んだ」が含まれる

完成版コード

序章の最終状態は examples/ch00/solution にある。npm ci と npm start で起動できる。演習 0-4 の解答は、runAdventure の rest の分岐と、formatEvent の rest の文である。

主要なファイルの読みどころ：

  • src/adventure.ts：序章では、規則（何が起きるか）と進行（順に処理する）の役割を1つのファイルが持つ。第1章で src/sim/ に移し、規則は src/rules/ に分ける。
  • src/narration/format.ts：叙述は出来事と名前の対応表だけから作り、ゲームの進行には関わらない。
  • src/content/scenario.ts：データだけを置く。ゲームを変えたいときは、まずここを書き換える。
