第1部 一瞬の行動 ／ 第2章

障害を乗り越える

同じ崖の前に立っても、登攀の得意なアリア、鉤縄を持つボルド、浮遊の魔法を使うセナでは、取れる行動が違う。この章では、行為を「データ」として書き、その人がいま使える行為を「規則」で計算して求める。

  • 目安 3〜4時間
  • TypeScript：判別共用体、Record、satisfies
  • Git：ブランチ

今回作るもの

崖の前にいる3人について、使える行為の一覧を、環境の3つのパターン（通常・嵐で蔦が切れた・岩の突起が崩れた）ごとに表示するCLIを作る。続けて行為を1つずつ実行し、そのたびに誰の手に新しい行為が現れ、何が消えたかを示す。

期待される動作：

  • 同じ崖でも、技能（登攀・浮遊）と持ち物（鉤縄）によって、使える行為が人ごとに変わる。
  • 環境が変わる（蔦が切れる、岩の突起が崩れる）と、同じ人でも使える行為が変わる。
  • ある人の行為が環境を変え、別の人に新しい行為を生む。ボルドが鉤縄を掛けると、アリアに「鉤縄を登る」が現れる。
  • 行為のログには、何が変わったか（体力 20→19、鉤縄：巻かれている→掛かっている）が残る。

出発点

演習用コード examples/ch02/starter から始める。第1章の完成版に、この章の規則（src/rules/）と崖のデータ（src/content/cliff.ts）を加えたものである。規則は完成した状態で入っている。演習では、規則には手を加えず、データを書き換えたり足したりする。

第1章の完成版との主な差分：

ファイル変更内容
src/domain/types.ts変更物・場所・能力・条件・効果・行為・アフォーダンスの型。パラメータを Record<string, number> に一般化
src/rules/conditions.ts新規条件の評価 evaluate と、日本語の説明 describeCondition
src/rules/effects.ts新規効果の適用 applyEffects
src/rules/transitions.ts新規閾値による状態遷移 applyTransitions
src/rules/affordances.ts新規checkAction、availableAffordances、sceneOf
src/rules/apply.ts新規行為の実行 applyAction
src/content/cliff.ts新規崖のカタログ、人物3人、環境の3パターン
src/rules/combat.ts ほか変更パラメータを param() で読むように直した
tests/architecture.test.ts新規モジュールの依存の向きを確かめる

第1章の戦闘と序章の冒険は、npm start -- --mode battle と npm start -- --mode adventure で引き続き動く。

演習

動作例を見る → データを改造する → 新しい行為を自力で追加する → 完成版と照合する、の順に進める。使う構文と規則の中身は必要な知識にまとめた。

必須演習 2-1 動作例を見る

実行するコマンド：npm start

出力の「崖下（通常）」の3行を読み、次の問いに答える。答えはデータ（src/content/cliff.ts）の中にある。

  1. セナが「蔦をつたって岩棚へ」を使えないのはなぜか。出力の「使えない」の行と、行為 climb:vine の pre を見比べる。
  2. 「嵐で蔦が切れた」では、なぜアリアとボルドの両方から蔦の行為が消えるのか。蔦の state と、climb:vine の条件 { type: 'state', of: 'vine', is: 'intact' } を見る。
  3. デモの3手目で、蔦の状態が「無傷→切れた」に変わった。行為の効果には状態を変える指定がない。何が状態を変えたのか（ヒント：蔦の transitions）。

必須演習 2-2 データを改造する

編集するファイル：src/content/cliff.ts

規則のコードには触れず、データだけを書き換えて、出力がどう変わるかを予想してから確かめる。1つ試したら元に戻す。

  1. ボルドの capabilities を { climb: 3 } にする → 「崖を直接よじ登る」がボルドの一覧に加わる。
  2. 蔦の params を { strength: 3 } にする → デモの3手目で蔦が切れず、ボルドには「蔦をつたって岩棚へ」が残る。
  3. セナの params の mana を 3 にする → 魔力が足りず、セナの一覧が「（できることがない）」になる。コストが前提条件として働くことを確かめる。

必須演習 2-3 跳躍の能力と行為を自力で追加する

編集するファイル：src/content/cliff.ts（2か所の TODO）

新しい能力「跳躍」（id: 'jump'）と、行為 jump:ledge を追加する。

項目値
ID・表示名jump:ledge・岩棚へ跳び上がる
前提条件崖下にいる、跳躍Lv2以上
効果行為者を岩棚へ移す
コスト体力2

演習 2-1 の climb:vine の書き方が手本になる。追加したら npm run test:exercises を実行する。テストは「跳躍2の人物が崖下にいるとき、使える行為に jump:ledge が加わる」ことなどを確かめる（tests/exercises/jump.test.ts）。

注意

この演習では src/rules/ を編集しない。新しい手段が「データを足すだけで」増えることが、この章の要点である。評価器に if (action.id === 'jump:ledge') のような分岐を書きたくなったら、データの書き方を見直す。

必須演習 2-4 完成版と照合する

テストが通ったら、完成版のデータと見比べる。条件の順序が違っても、結果は同じになる（条件はすべて満たす AND で評価される）。最後に変更をコミットする。

発展演習 2-A 倒木を足す

崖下に物「倒木」（log、状態 lying／leaning）を置き、「倒木を崖に立て掛ける」（倒木を leaning にする）と「倒木を伝って岩棚へ」（倒木が leaning、登攀Lv1以上）の2つの行為を足す。誰かが立て掛けると、別の人に新しい行為が現れることを確かめる。どの人物に、どの行為の組合せで新しい突破手段が生まれるかを表にしてみる。

発展演習 2-B 理由の説明を読みやすくする

describeCondition は、状態の条件を「状態が「intact」であることが必要」と表示する。状態名の表示名（stateLabels）を引数で渡せるようにし、「蔦が「無傷」であることが必要」と表示する。tests/conditions.test.ts にテストを足してから直す。

必要な知識

判別共用体：条件や効果を「データ」で書く

条件や効果は関数ではなく、type という目印を持つオブジェクトで書く。switch (c.type) で分けると、それぞれの分岐の中では、その形にしかないフィールドを使える。関数と違い、JSONにそのまま保存でき、日本語で説明でき、あとから分析できる。

Record と「無いものは0」の規則

パラメータは Record<string, number>（文字列のキーと数値の組）で持つ。この教材の設定（noUncheckedIndexedAccess）では、読んだ値は number | undefined になる。毎回 ?? 0 と書く代わりに、規則を関数 param() の1か所に集める。

不変更新：元の世界を書き換えない

applyAction は、引数の世界状態を書き換えず、複製を変えて返す。第3章の探索では、1つの状態から何通りもの「もしこうしたら」を試すので、元が変わらないことが欠かせない。

satisfies：型に合うかだけを確かめる

export const cliffCatalog = { ... } satisfies Catalog; は、値が Catalog の形に合っているかを型チェックで確かめる。書き間違い（tpye: 'at' など）はここで見つかる。演習 2-3 で行為を足したときに型エラーが出たら、まず条件や効果の type の綴りを確かめる。

評価器の中身：条件を評価し、使える行為を列挙する

条件1つを評価する evaluate が、規則の中心である。参照 '$actor'（行為者）や '$target'（対象）は文脈から、それ以外はエンティティのIDとして解決する。解決できない参照を含む条件は偽になる。

コスト（体力3など）は、評価器が自動で2つに展開する。前提条件「体力が3以上」と、効果「体力を3減らす」である。作者がコストを条件として重ねて書く必要はない。

使える行為は ActionId の辞書順に並べる。順序を固定しておくと、同じ入力から常に同じ結果が得られる。第3章の探索の再現性は、この順序に依存する。

行為の実行：コスト → 効果 → 状態遷移

applyAction は、前提条件を確かめ、世界を複製し、コストを引き、効果を書かれた順に適用する。最後に、変化した物について状態遷移の規則を評価する。すべての変化は Change として、何による変化か（via：コスト・効果・遷移）とともに記録する。

Git：ブランチ

演習ごとにブランチを切ると、試した変更を本流（main）と分けておける。演習 2-2 のような「試して元に戻す」改造は、ブランチで行い、不要になったら捨てればよい。

文献コラム

状態・パラメータと、「関係」としてのアフォーダンス

Pinchbeck（2009）は、ゲームの物を「状態」と「パラメータ」で記述した。パラメータが閾値に達すると、状態が切り替わる。叩くと壊れる木箱が典型例で、耐久値が0になると「壊れた」状態に移り、その状態で可能な行為が変わる。この章の蔦は、その木箱と同じ構造をしている。

Baker & Roberts（2025）は、アフォーダンスを、能力を持つエージェントと環境との関係として捉えた。崖そのものが「登れる」性質を持つのではない。登攀Lv3のアリアと崖の組では「直接登る」が成り立ち、登攀Lv0のセナと崖の組では成り立たない。そのため、この章ではアフォーダンスを保存せず、そのつど計算で求める。

文献の概念この章の実装
状態（Pinchbeck）
物の state と、取りうる状態の宣言 states（蔦の intact／torn）
パラメータ（Pinchbeck）
params: Record<string, number>（蔦の strength、人物の stamina）
閾値による状態遷移（壊れる木箱）
transitions と applyTransitions。蔦の強度が0以下で torn に移り、変化は via: 'transition' として記録される
重要度（gameplay／story）
significance: { play, story }。崖は {3, 1}、岩の突起は {1, 0}（この章では記録するだけで、規則には使わない）
アフォーダンス＝関係（Baker & Roberts）
行為の定義 × 人物の能力・パラメータ × 環境の状態から求める availableAffordances。結果は保存しない
能力（行動的・認知的）
CapabilityDef の kind。この章の登攀・浮遊・跳躍はすべて行動的
環境集合（Pinchbeck）
sceneOf が返す場面（その場所にいる人物と物）

ボルドが鉤縄を掛けると、アリアに「鉤縄を登る」が現れる。環境の変化が他者のアフォーダンスを変えることを、コードの分岐ではなくデータだけで表せた。ただし、この章では、人物の目に入らない物も条件に書けば使える。知覚の範囲（見えているか）は条件として明示する方針であり、扱いは第10章で見直す。

Pinchbeck, D. (2009). An affordance based model for gameplay. Proceedings of DiGRA 2009.

Baker, B. & Roberts, S. (2025). Understanding Agent Complexity Through Affordances. Minds and Machines, 35:51.

動作確認

  1. npm start を実行し、出力が今回作るものの出力例と一致することを確かめる。
  2. 演習 2-3 を解いた後も、出力は変わらない（跳躍を持つ人物がいないため）。src/content/cliff.ts のセナの capabilities に jump: 2 を足して実行し、セナの一覧に「岩棚へ跳び上がる[体力2]」が加わることを確かめる。確かめたら元に戻す。
  3. npm start -- --mode battle と npm start -- --mode adventure を実行し、第1章と序章の出力が変わっていないことを確かめる。

確認する観点：

  • 一覧の違いが、人（技能・持ち物）と環境（蔦・岩の突起の状態）のどちらから来ているかを説明できる。
  • 行為のログで、コストによる変化（体力）と、効果・遷移による変化（鉤縄・蔦の状態）を見分けられる。
  • 規則（src/rules/）を変えずに、データだけで新しい手段を増やせた。
